# S06 — recuperación y reversión propuestas

Estado 2026-10-31: **NO EJECUTADA**. Sólo runbook para revisión; requiere Gate 6, Gates 1–5 válidos para su alcance, consola probada, custodio de claves y otra VM/instancia nueva autorizada. No hay scripts de restore ejecutables en S06-A ni se modifica backup.sh S03. RPO, RTO, retención, ventana de indisponibilidad y presupuesto siguen sin aprobar; medir y ratificar, no prometer tiempos.

## Preparación y consola fuera de banda

1. Registrar alias de VM y hashes de imagen, disco, release, lock, isolation y perfil S04/S05; mantener mapping privado a ID real. Separar autorización de cambios y aprobación de evidencia. Verificar que la consola/rescue no depende de firewall, VPN o SSH del guest y que el operador puede aislar/apagar desde el plano de gestión.
2. Custodiar medios OS/Node/MariaDB/nginx/age/cache offline verificados, release actual y anterior verificados, unidades exactas y expediente de identidad vacío. No incluir secretos en la ISO/PR ni compartir mounts con producción. Clave age privada fuera de VM; el operador la maneja por el canal aprobado, sin prompts automatizados ni copiarla a logs.
3. Antes de futuras pruebas de red, demostrar rescate en guest denegado. Si se pierde acceso: usar consola externa autorizada, preservar estado y capturas revisadas; no abrir SSH público, no borrar reglas para recuperar acceso y no hacer flush del firewall. Si no es recuperable sin cambiar controles, apagar/desconectar por consola y pedir aprobación de reconstrucción nueva.

## Ante fallo de aplicación/build o integridad

1. Detener avance del gate y registrar FAIL; no reiniciar repetidamente ni usar un build con guardas desactivadas. S03 limita reinicios; inspeccionar cgroup y logs sólo con operador autorizado, sin exportar env/journal completo.
2. En caso de release alterada, detener app/proxy conservando firewall y MariaDB aislada. Congelar copia de evidencia revisada; no ejecutar scripts de la release sospechosa para verificarla. Usar verificador S05 confiable y hash independiente.
3. Si sólo falla la aplicación, comprobar ausencia de descendientes y listener mediante unidad/cgroup, sin matar procesos de otras cuentas/unidades. No detener MariaDB como efecto colateral de stop Next. Si no hay control de procesos, mantener servicio sin aceptar tráfico y escalar al operador; no declarar parada PASS.
4. Restaurar una **release previa ya verificada**, tras autorización, en ruta de copia controlada sin symlinks ni sobreescritura de archivos activos; restaurar ancla de hash correspondiente en configuración externa y revalidar S02. Los secretos sintéticos y la identidad DB deben seguir coherentes. No introducir un rollback de datos, migración, cambios de grants o desbloqueo. Si no existe release previa válida, detener y conservar NO EJECUTADA para K1.
5. Comparar estado DB autorizado antes/después (metadata/conteos/grants y cuenta bloqueada). Una comparación de conteos sola no prueba identidad de todos los datos: incorporar hashes deterministas de filas sintéticas mediante herramienta revisada, sin publicar contenidos sensibles. Tras verificación independiente y autorización, iniciar sólo loopback y repetir smoke negativo. No afirmar login funcional con ACCOUNT LOCK.

## Backup lógico cifrado

1. Validar base/marker/datadir/custodia y autorización antes de acceder. El backup S03 usa socket administrativo local y mariadb-dump de una sola base, no credenciales runtime. La tarea de backup tiene privilegios separados; scripts de inspección S06-A nunca la ejecutan.
2. Demostrar que app/proxy y cualquier writer externo/administrativo están detenidos durante el respaldo. S03 Conflicts detiene unidades conocidas; eso **no acredita por sí solo** ausencia de writers ajenos o DDL. Ensayar consistencia de tablas InnoDB y rechazar cambios concurrentes. No ampliar grants ni asumir snapshot de volumen consistente.
3. Revisar archivos concretos S03 incluidos (dump lógico, uploads sintéticos, isolation, SHA256SUMS); aplicar age con destinatario público aprobado. El entorno y contraseñas runtime no están en ese paquete: planificar nueva provisión de secretos sintéticos desde custodio para restauración. Recipientes/llaves sin ratificación bloquean Gate 6.
4. El script mantiene staging plaintext temporal y `.partial` si hay fallo: revisar permisos, espacio, interrupciones y limpieza segura en laboratorio. No afirmar que no quedan plaintext/partials hasta comprobarlo; no borrar evidencia automáticamente. Nunca copiar staging plaintext al PR o almacenamiento no cifrado.
5. Confirmar integridad ciphertext con hash externo custodiado, archivo final sólo tras éxito, y prueba de descifrado en destino aislado autorizado. Transferencia offline o canal posterior aprobado, sin abrir egress desde el sandbox. Snapshots del proveedor son un complemento, no sustituto del backup probado.

## Restauración en otro destino completamente nuevo

1. Autorizar separadamente nueva VM/disco/instancia de ensayo; repetir procedencia, datadir vacío, mounts, red, consola, cuentas y versiones. Ninguna base existente, ni siquiera otra QA, es destino permitido. Conservar VM original aislada, sin conexiones a la restaurada; no reutilizar su journal de instalación.
2. Verificar hash externo, descifrar con custodia fuera de logs en almacenamiento temporal privado aislado y revisar manifiesto/archivos. Rechazar links, rutas fuera del destino, dispositivos, extras y extracción encima de rutas existentes. No ejecutar SQL como parte de extracción.
3. Inspeccionar dump completo con protocolo revisado antes de importar: sólo esquema/tablas/filas esperados S04. Rechazar usuarios/grants, acceso a otros esquemas, DEFINER/routines/events/triggers inesperados, operaciones de archivos o configuración global y datos no sintéticos. Conservar checks de versión y semántica de dump. Este verificador/restaurador aún **no está implementado ni probado**: es bloqueo de J2, no autorización para usar un cliente SQL directamente.
4. Diseñar y auditar un protocolo específico de restore que verifique identidad vacía antes de la primera modificación, marque el destino como intento exclusivo, cree sólo base autorizada, use cuenta administrativa de instalación y detenga al primer error. No reutilizar `prepare` S04 sobre una DB importada: por diseño rechaza bases existentes. DDL puede dejar parciales; conservarlos/journal y no reutilizar ese destino tras fallo. Crear otra instancia nueva sólo con nueva autorización.
5. Verificar esquema, índices, FK/CHECK, antijoins, marker/filas sintéticas y hashes contra backup y plan. El marker restaurado por sí solo no acredita identidad nueva: contrastar el dossier físico/datadir y cadena de custodia. Aprovisionar secretos sintéticos nuevos e isolation coherente mediante procedimiento S02/S03 revisado, sin adoptar claves de una máquina desconocida.
6. El dump de una DB no respalda automáticamente cuentas/grants de servidor. El protocolo revisado debe reconstruir **sólo** el perfil S04 SELECT por tabla, con marcador protegido y ACCOUNT LOCK; no importar mysql.* ni cuentas del origen. Verificar restricciones efectivas sin interpretar denegación por cuenta bloqueada como prueba de todos los grants. No desbloquear ni crear cuenta de sustitución.
7. Repetir integridad de release, controles de red y negativos; positivas HTTP/UI siguen bloqueadas hasta decisión técnica aparte. Medir RPO/RTO realmente y comparar con objetivo previamente aprobado. Auditor revisa resultados antes de declarar recuperación PASS. No arrancar automáticamente después de backup/restore y no habilitar API PriceSmart.

Las fases privilegiadas descritas son tareas futuras de operadores expresamente autorizados. Esta documentación no aprueba modificaciones, instalación, provisión, ejecución SQL, creación de VM, DNS, firewall, merge ni despliegue.
